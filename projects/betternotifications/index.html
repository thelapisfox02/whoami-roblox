BetterNotifications

Properties
RoleOpen source module
AuthorshipAI-assisted
Key numberMIT, public repository

Roblox experience notifications with a send queue that never yields the caller, a token-bucket rate limit, jittered retry backoff, cross-server dedupe, durable scheduling on MemoryStore with a DataStore mirror, and an opt-in registry that says openly it is a guess, not a fact. A dry-run mode and a live-send test harness are included, and the README states the platform limits it cannot get around.

What I did

  • I set the scope and the API shape: how opt-in discovery works, which targets it supports, fire-and-forget Send, and how deep the analytics goes.
  • I wrote the first usage snippet, and the module had to run it unchanged.

What it does

  • Send never yields the caller: it queues, and one rate-limited worker drains the queue.
  • Cross-server dedupe is a MemoryStore compare-and-set per user per day. It fails open on purpose: a duplicate costs one API call, while failing closed would silently drop real notifications.
  • Long-horizon schedules survive a MemoryStore flush: they are mirrored to a DataStore and replayed when a server starts.
